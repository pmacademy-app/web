# PM Academy — Refactoring & Code Review

Load `00-pm-academy-core` alongside this skill.

---

## 1. When to Refactor

**DO refactor when:**
- Business logic is inside a React component (extract to `lib/` business modules).
- Duplicated queries or data operations exist across pages/routes (extract to `lib/data/` data-fetching helpers).
- A function does too many things (split by concern).
- Magic numbers or strings are hardcoded (extract to constants).
- `any` type is used (replace with proper TypeScript definitions).
- A server component contains `"use client"` unnecessarily (remove it).

**DO NOT refactor when:**
- You are also adding features (separate commits for refactoring vs. features).
- The "elegance" makes the code harder for a solo founder to understand quickly.
- The change introduces new dependencies or frameworks.

---

## 2. The Solo-Founder Readability Test

Before refactoring, ask: **"Could a solo founder (or an AI assistant with no memory of this session) understand this code in 5 minutes?"**

Cleverness is not a goal. Boring, explicit, readable code wins.

## 3. Data Fetching Abstractions (`lib/data/`)

To prevent duplicate queries, place database selectors in `lib/data/` files. Never fetch raw Supabase queries in client components.

```typescript
// ✅ CORRECT — lib/data/user-progress.ts
import { createServerSupabaseClient } from '@/lib/supabase'

export async function getUserLessonProgress(
  supabase: ReturnType<typeof createServerSupabaseClient>,
  userId: string,
  lessonSlug: string
) {
  return supabase
    .from('user_lesson_progress')
    .select('*')
    .eq('user_id', userId)
    .eq('lesson_slug', lessonSlug)
    .single()
}

// ✅ Call from Server Component
import { createServerSupabaseClient } from '@/lib/supabase'
import { getUserLessonProgress } from '@/lib/data/user-progress'

export default async function Page() {
  const supabase = createServerSupabaseClient()
  const { data: { user } } = await supabase.auth.getUser()
  if (!user) return null
  
  const { data: progress } = await getUserLessonProgress(supabase, user.id, 'lesson-001')
  // ...
}
```

## 4. TypeScript Code Quality & Database Types

### Database Type Generation
This project integrates autogenerated Supabase type definitions. Do not define raw table schemas manually.

```typescript
// ✅ CORRECT — import from autogenerated Database definitions
import { Database } from '@/lib/supabase'

export type UserRow = Database['public']['Tables']['users']['Row']
export type UserProgressRow = Database['public']['Tables']['user_lesson_progress']['Row']

export function processProgress(progress: UserProgressRow) {
  const score = progress.quiz_score ?? 0 // safe null handling
  // ...
}
```

### TypeScript Safety Standards
- **Zero `any` usages.** If a type is unknown, use `unknown` or define a strict generic/fallback type.
- **Strict Null Safety:** Always handle nulls using nullish coalescing `??` or optional chaining `?.` explicitly.
- **Lookup Tables:** Mark all static lists with `as const` assertions to allow TypeScript to infer literal types.

## 5. Component Review Checklist

- [ ] `"use client"` is only present if state/effects/browser APIs/Framer Motion require it.
- [ ] Data fetching happens in Server Components, passing presentational data down as props.
- [ ] Next.js 16 async route params are correctly `await`ed.
- [ ] All props are typed without `any`.
- [ ] Accessibility: keyboard nav works, focus indicators visible, ARIA labels are added.
- [ ] Framer Motion animations check `useReducedMotion()`.
- [ ] Images use `next/image` and fonts use `next/font`.
- [ ] User-facing strings are not hardcoded inside JSX (moved to a constants file).

---

## 6. API Route Review Checklist

- [ ] `supabase.auth.getUser()` is called FIRST. No usage of deprecated `getSession()`.
- [ ] `user.id` is derived from session, not the request body.
- [ ] Payloads are validated with Zod schemas.
- [ ] DB modifications use triggers for caches, maintaining ledger history.
- [ ] Database functions default to `SECURITY INVOKER`. If `SECURITY DEFINER` is used, search path is explicitly defined.
- [ ] Error responses do not expose internal DB schemas or tracebacks.

---

## 7. Refactoring Workflow

```bash
# 1. Write or run unit tests for the current code to lock in behavior.
# 2. Refactor in small, logical steps.
# 3. Run unit tests after EVERY refactoring step.
# 4. Commit refactoring steps separately from feature work.

git commit -m "refactor: extract user progress query to lib/data/user-progress.ts"
git commit -m "refactor: add strict database type annotations to XP recorder"
```
